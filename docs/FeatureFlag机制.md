# FeatureFlag 机制

> 目的：把**功能发布**和**功能启用**解耦。新功能出了异常，改一个 JSON 里的 `false` 就能立刻下线，不用改代码、不用重新部署、不用重启。

## 一分钟上手

### 方法一：双击工具（推荐，不用记语法）

双击 **`flags.cmd`**，出现菜单：

```
  ┌─────────────────────────────────────────────────────────┐
  │  GitHub 周报 · 功能开关                                 │
  └─────────────────────────────────────────────────────────┘

   [1] ● 开卡片展开简报                 关掉后卡片只剩标题+概括
   [2] ● 开「对你的用处」段               依赖上面那个
   [3] ● 开标签行                    依赖 expand
   [4] ● 开相关度彩色圆点                与你相关/可借鉴/了解即可
   [5] ● 开想法输入框                  关掉后不能提交想法
   [6] ● 开实践反馈块                  关掉后只显示"等待实践"

   [a] 全部开启      [z] 全部关闭      [s] 看线上状态
   [q] 退出
```

按数字切换，改完立刻生效，刷新浏览器就能看到。按 `s` 能看到服务端实际生效状态。

### 方法二：直接改文件

编辑 `config/flags.json`，把对应 `enabled` 改成 `false`，保存。刷新页面即可。

### 方法三：看状态 / 紧急全关

**看当前状态**：浏览器打开 `http://127.0.0.1:11436/api/flags`

**全部关掉（紧急）**：设置环境变量 `GHW_FLAGS_OFF=1` 后重启一次。

## 现有开关

| 开关 | 控制什么 | 关闭后的行为 |
|---|---|---|
| `briefing.expand` | 卡片可展开看简报 | 卡片变成静态条目，只显示标题+概括+star+语言 |
| `briefing.forYou` | 「对你的用处」绿色高亮段 | 该段不渲染（**依赖 expand**） |
| `briefing.tags` | 标签行 | 不渲染（**依赖 expand**） |
| `relevance.indicator` | 相关度彩色圆点 | 不渲染圆点，其余照常 |
| `ideas.submit` | 想法输入框 + `POST /idea` | 页面无输入框，接口返回 503 |
| `reports.display` | 实践员反馈块 | 只显示「等待实践」，不显示已回写的结论 |

## 优先级（三级覆盖）

```
环境变量 GHW_FLAG_<KEY>   ← 最高，适合临时压测/紧急
        ↓
config/flags.json         ← 日常用这个，热加载
        ↓
flags.mjs 里的 DEFAULTS   ← 出厂默认，改它等于改基线
```

环境变量命名规则：`briefing.forYou` → `GHW_FLAG_BRIEFING_FORYOU`

支持的值：`1/true/on/yes/y` 为开，`0/false/off/no/n` 为关。

## 热加载怎么做到的

`flags.mjs` 缓存了 `flags.json` 的 **mtime**（修改时间）：

- 每个请求调 `getFlags()`
- 发现 mtime 变了 → 重新读文件解析
- mtime 没变 → 直接用缓存，零 IO 开销

所以**改文件后下一个请求就生效**，进程不用重启。测试里专门验证了这一点（`进程未重启（startupLog 只有一次就绪行）`）。

## 依赖级联

有些开关天然有依赖：

```js
const DEPENDS_ON = {
  'briefing.forYou': 'briefing.expand',
  'briefing.tags': 'briefing.expand',
};
```

父开关关闭时，子开关自动视为关闭，且 `/api/flags` 里能看出原因：

```json
"sources": {
  "briefing.forYou": "cascade:briefing.expand"
}
```

**为什么要这个**：如果只关 `expand` 而 `forYou` 显示为开，日志会误导排查。级联让「实际生效值」始终自洽。

## 关闭时如何保留原有逻辑

**代码一行都没删**，只是加了 `if` 判断。证据（测试会自动校验）：

- `function submitIdea` 仍在源码里
- `function toggle` 仍在源码里
- 「对你的用处」文案仍在源码里
- 「实践反馈」块仍在源码里

关闭走的是**运行时分支**，不是删代码。这是 FeatureFlag 和「删功能」的本质区别——随时能开回来。

## 容错设计（三层保护）

| 场景 | 行为 |
|---|---|
| `flags.json` 不存在 | 全用 `DEFAULTS`，页面正常 |
| `flags.json` 格式错误 | **沿用上次成功解析的值**，`/api/flags` 报 `error`，页面正常 |
| 某个 key 类型不对 | 该 key 回落到默认值，其余不受影响 |
| 进程本身崩了 | 与开关无关，走原有守护方案 |

**核心原则：开关系统本身绝不能成为新的故障点。** 所以任何异常都降级到「上次有效值」或「默认值」，绝不返回 500。

## 一次真实的设计缺陷（已修）

**问题**：最初把想法输入框放在了展开区 `.body` 里面。结果关掉 `briefing.expand` 后，整个展开区消失，**连带把还开着的 `ideas.submit` 也弄没了**——用户看到开关是开的，但界面上没入口。

**修法**：收起态单独渲染一个 `.flatfoot` 容器装输入框，让两个开关真正正交。

**教训**：加开关前必须问「**这个开关关掉，会不会连带弄坏别的开关？**」——DOM 嵌套层级会偷偷制造隐性依赖。测试里补了两条正交性用例守住这条线。

## 边界与取舍

**做了什么**

- 6 个开关覆盖所有新增的交互能力
- 热加载、级联、容错、状态 API、测试套件
- 页面顶部告警条：有几项被关、具体是哪些

**没做什么（有意）**

| 没做 | 原因 |
|---|---|
| 用户级灰度（A/B） | 单用户本地工具，没有灰度场景 |
| 开关管理界面 | 改 JSON 比做界面更直接，界面的成本不值 |
| 远程下发 | 本地服务，没有远端配置源 |
| 开关变更审计日志 | 单人项目，`git diff` 就是审计 |
| 定时自动回滚 | 需要监控指标支撑，当前没有指标 |

## 文件位置

| 文件 | 职责 |
|---|---|
| **`flags.cmd`** | **双击入口（交互菜单）** |
| **`flag-tool.ps1`** | 交互工具本体（带 BOM 保存，否则中文乱码） |
| `flags.mjs` | 开关核心：三级覆盖、级联、容错、mtime 缓存 |
| `config/flags.json` | 日常修改入口（**必须无 BOM**） |
| `server.mjs` | 在每个渲染点读开关，做降级分支 |
| `test-flags.mjs` | 56 项自动化测试，覆盖开/关/热加载/级联/正交性/容错 |
| `docs/shot-on.png` | 全开状态截图 |
| `docs/shot-off.png` | 关闭状态截图（含告警条） |

> **两个文件对 BOM 的要求正好相反**，这是 PowerShell 5.1 的坑：
> - `flag-tool.ps1` **必须有 BOM**，否则中文注释被误解析，语法报错
> - `config/flags.json` **必须无 BOM**，否则 Node 的 `JSON.parse` 失败
