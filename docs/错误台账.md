## E001 · GitHub trending 页面 301 无限循环

**日期**：2026-11-23
**现象**：

```
[redirect -> https://github.com/trending?since=weekly ]
[redirect -> https://github.com/trending?since=weekly ]
... 重复 5 次 ...
status: 301 bytes: 0
```

明明重定向的目标就是它自己，跟进去还是 301。

**原因**：GitHub 对无 Cookie / 无正常浏览器特征的 `trending` 请求做了规范化跳转，某些情况下会形成自指循环。这个页面是给浏览器渲染用的，不是一个稳定的数据接口。

**修法**：弃用它，改用 **GitHub Search API**：

```
q=created:>=<一周前>&sort=stars&order=desc&per_page=10
```

即「本周新建 + star 最多」，这是最接近「周热榜」的官方口径，且直连可用、无需认证。

**教训**：**别抓 HTML 当日志数据源。** 有官方 API 就用官方 API——哪怕语义不完全一致，稳定性也值。

**留档**：`tools/gh-trending.mjs` 保留但已废，别用。

## E002 · PowerShell 测中文变问号，误判为程序 bug

**日期**：2026-11-23
**现象**：用 `Invoke-WebRequest` 提交中文想法，落盘的 JSON 是：

```json
{"repo":"test/fake","text":"????????"}
```

一度以为 Node 服务端编码坏了。

**原因**：PowerShell 5.1 的 `Invoke-WebRequest` 在构造请求体时按本地代码页（GBK）编码，中文全部变成 `?`。**服务端完全正常**，是测试工具的问题。

**修法**：验证中文链路必须走浏览器（页面实测 UTF-8 正确）。如果一定要用命令行测，得显式指定 UTF-8：

```powershell
$body = [System.Text.Encoding]::UTF8.GetBytes($json)
```

**教训**：**测试工具的编码问题，最容易误判成代码 bug。** 换个客户端交叉验证，能省半小时。

## E003 · 页面刷新后卡片全部收起

**日期**：2026-11-23
**现象**：展开某张卡片看完简报，按 F5 刷新，所有卡片回到收起状态。

**原因**：展开状态只在 DOM 的 class 里（`.card.open`），没有持久化。

**暂时不修**，理由：每次看都是新的，收起状态反而适合扫读 10 条。如果 Kairo 觉得烦，加 localStorage 记住展开的 repo 名即可。

**教训**：有些「bug」其实是合理取舍。**先问是不是真问题，再决定修不修。**

## E004 · 服务关掉终端就没了

**日期**：2026-11-23
**现象**：用 `Start-Process -WindowStyle Hidden` 起的 `node server.mjs`，在 DSH 会话结束后进程消失，页面打不开。

**原因**：与嵌入服务同一个问题——沙箱/会话结束时子进程树被回收。

**当前状态**：定时任务里会检查并拉起（`Start-Process`），但没有独立的守护进程。Kairo 手动关闭会话后可能要重新起。

**候选修法**（未做）：参考 `D:\dsh-workspace\embedding` 的方案——Windows 计划任务 + 幂等 watchdog（健康检查失败才拉起），那次已验证有效。

**教训**：**常驻服务必须有外部守护。** 靠会话内起的进程活不过会话。

## E005 · 简报 repo 名对不上，页面退化显示 GitHub 原始描述

**日期**：2026-11-23（设计时预判，未实际触发）
**现象**：如果 `briefings-*.json` 里的 `repo` 和 `weekly-*.json` 不完全一致，`loadIssue()` 匹配不上，该卡片没有 summary/whyHot/brief/forYou，退化成 GitHub 原始 desc。

**原因**：`loadIssue()` 用 repo 全名（`owner/name`）做关联 key。

**修法**：写简报时**直接从 weekly JSON 里复制 repo 字段**，不要手打。大小写敏感。

**教训**：用业务主键做关联时，**永远从源数据复制，不要重新输入**。

## E006 · 反馈关联不上（ideaAt 差一个字符）

**日期**：2026-11-23（设计时预判，未实际触发）
**现象**：`reports.jsonl` 里有记录，但页面不显示反馈，一直显示「⏳ 已收到，等待实践」。

**原因**：`readReports()` 用 `ideaAt` 精确匹配 `ideas.jsonl` 的 `at` 字段。时间戳差一位、时区格式不同、或者手动改过，就匹配不上。

**修法**：实践员写 report 时，**从 ideas.jsonl 里原样复制 `at` 值**，不要自己生成时间。

**教训**：同上——**关联键永远复制，不要重造。**

## E007 · 中文注释导致 PowerShell 脚本解析失败

**日期**：2026-11-23（在嵌入服务的 watchdog 上踩到，本项目警戒）
**现象**：

```
Unexpected token '}' in expression or statement.
```

语法看着完全正确，但 PowerShell 5.1 就是报错，且报错位置莫名其妙。

**原因**：PowerShell 5.1 读取**无 BOM 的 UTF-8 文件**时，中文注释会被按本地代码页误解析，导致字符边界错乱、引号配对失败。

**修法**（嵌入服务那边已验证）：脚本内容全用 **ASCII**，或保存为 **UTF-8 with BOM**。

**本项目的态度**：`server.mjs` 和 `tools/*.mjs` 都是 Node 跑的，**不受影响**（Node 默认 UTF-8）。但**如果以后加 PowerShell 脚本，必须注意这一条**。

**教训**：跨语言项目里，**编码约定要按运行时分别定**，不能一套通吃。

## E008 · 加开关反而弄坏了另一个开关（正交性缺陷）

**日期**：2026-11-23
**现象**：把 `briefing.expand` 设为 `false` 后，页面上想法输入框也不见了。但 `/api/flags` 明确显示 `ideas.submit = true`。

**原因**：输入框 HTML 写在了展开区 `.body` 内部。关掉 `expand` 时整个 `.body` 不渲染，输入框被连带带走——**DOM 嵌套层级制造了隐性依赖**。开关本身没错，是布局位置错了。

**修法**：收起态单独渲染 `.flatfoot` 容器装输入框，让两个开关真正正交：

```js
if (!F['briefing.expand']) {
  const flatComposer = F['ideas.submit'] ? `<div class="flatfoot">…输入框…</div>` : '';
  return `<article class="card flat">…${flatComposer}</article>`;
}
```

测试补两条正交性用例：

- 关 `expand` + 开 `ideas.submit` → 无 `.body`，**有** `.composer`
- 开 `expand` + 关 `ideas.submit` → 有 `.body`，**无** `.composer`

**教训**：加开关前必须问「**这个开关关掉，会不会连带弄坏别的开关？**」DOM 嵌套、函数调用链、共享状态变量都会偷偷制造依赖。**开关必须正交，否则数量一多就是灾难。**

## E009 · PowerShell 写 JSON 带 BOM，导致开关改动不生效

**日期**：2026-11-23
**现象**：改了 `config/flags.json` 把开关设成 `false`，刷新页面毫无变化，`/api/flags` 还显示 6/6 全开。

**原因**：用 `Out-File -Encoding UTF8` 写入，PowerShell 5.1 会**加上 BOM**（0xEF 0xBB 0xBF）。Node 的 `JSON.parse` 遇到 BOM 直接抛错，容错机制接管 → 沿用 `lastGood`（上次成功解析的值）→ 所以改动被静默忽略。

**有意思的是**：这正是容错机制在按设计工作——文件坏了也不让页面挂。但代价是**改动无声失效**，排查时容易误判成「热加载坏了」。

**修法**：写无 BOM 的 UTF-8：

```powershell
[System.IO.File]::WriteAllText($path, $json, (New-Object System.Text.UTF8Encoding($false)))
```

**排查技巧**：`GET /api/flags` 里看 `meta.error`。有值就是解析失败，改动没生效。

**教训**：**「容错」和「静默失败」只差一个可观测性。** 所以 `/api/flags` 必须暴露 `error`，页面上也要有告警条——不然机制再好也查不出问题。

## E010 · 测试断言用子串匹配，命中了 CSS/JS 里的同名字符串

**日期**：2026-11-23
**现象**：4 项测试失败，看起来像功能坏了：

- 「无告警条」失败——但页面上确实没显示告警条
- 「无展开按钮」失败——但按钮确实没渲染

**原因**：断言写的是 `page.text.includes('flagbar')` 和 `includes('展开简报')`。但：

- `flagbar` 命中了 `<style>` 里的 `.flagbar{...}` CSS 定义
- `展开简报` 命中了内联 `<script>` 里 `toggle()` 的字符串常量

**修法**：断言改成匹配**元素属性**而不是裸文本：

```js
// 错
!page.text.includes('flagbar')
// 对
!page.text.includes('class="flagbar"')
!page.text.includes('class="toggle"')
```

**教训**：**测网页内容时，绝不匹配裸文本。** 页面里同时存在 HTML、CSS、JS 三套字符串，裸文本匹配必然误判。要匹配带属性的完整标记。

## E011 · 同一个项目里两个文件对 BOM 的要求正好相反

**日期**：2026-11-23
**现象**：写好 `flag-tool.ps1`（交互工具），PowerShell 报 15 个语法错误：

```
表达式或语句中包含意外的标记"鍏虫帀鍚庡崱鐗囧彧鍓╂爣棰?姒傛嫭'"
哈希文本不完整。
```

中文全变成乱码，引号配对也乱套了。

**原因**：文件里全是中文菜单文案，而它被保存成了**无 BOM 的 UTF-8**。PowerShell 5.1 读无 BOM 文件时按本地代码页（GBK）解析，中文字节被拆错，引号配对失效。

**讽刺的是**：同一个项目里，`config/flags.json` 恰恰**必须无 BOM**，否则 Node 的 `JSON.parse` 会失败（E009）。

**修法**：

```powershell
# .ps1 脚本 → 必须带 BOM
[System.IO.File]::WriteAllText($f, $content, (New-Object System.Text.UTF8Encoding($true)))

# .json 配置 → 必须无 BOM
[System.IO.File]::WriteAllText($f, $json, (New-Object System.Text.UTF8Encoding($false)))
```

**教训**：**BOM 不是「全项目统一」的事，是按运行时分别定的**：

| 文件类型 | 由谁读 | BOM |
|---|---|---|
| `.ps1` | PowerShell 5.1 | **要** |
| `.json` | Node | **不要** |
| `.mjs` / `.js` | Node | 无所谓（Node 会跳过） |
| `.md` | 人/Git | 不要 |

判断依据是「**谁读它，它就对编码怎么敏感**」，不是「统一风格更好看」。

## E012 · PowerShell 打 GitHub API 全部 403

**日期**：2026-11-24
**现象**：想批量验证本周榜 10 个仓库是否真实存在，用 `Invoke-WebRequest` 打 `api.github.com/repos/...`，**10 个全返回 403**。

**原因**：本机 PowerShell 的 schannel TLS 栈与 GitHub 的握手不兼容（这个环境里早有先例：curl / Invoke-WebRequest 都不可靠，Node 的 OpenSSL 栈可以）。

**修法**：验证脚本改用 Node（`node tools/verify-repos.mjs`），10 个里 8 个存在、2 个 404。

**教训**：**这个环境里，凡是访问外部 HTTPS，优先用 Node 而不是 PowerShell。** 否则会得到"全都失败"的假象，浪费时间去查 token 和权限。

## E013 · CLI 守卫写成 `endsWith('star.mjs')`，被 import 时误触发

**日期**：2026-11-24
**现象**：`tools/e2e-star.mjs` 里 `import { setStar } from './star.mjs'`，运行 e2e 脚本却打印出 `star.mjs` 的用法提示并退出 1。

**原因**：`star.mjs` 底部的 CLI 守卫写的是：

```js
if (process.argv[1] && process.argv[1].endsWith('star.mjs')) { ... }
```

但被 import 时 `process.argv[1]` 是**运行的那个脚本**（`e2e-star.mjs`）。而 `'...e2e-star.mjs'.endsWith('star.mjs')` 恰好为 `true`——后缀撞车了。

**修法**：用 `import.meta.url` 取自己的真实文件名来比较：

```js
import { fileURLToPath } from 'node:url';
const SELF = path.basename(fileURLToPath(import.meta.url));
const ENTRY = path.basename(process.argv[1] || '');
if (ENTRY === SELF) { /* CLI 逻辑 */ }
```

**教训**：**判断"是不是在直接运行"要用模块自身的路径，不能靠 argv[1] 的后缀。** `endsWith` 在文件名有公共后缀时（`star.mjs` / `e2e-star.mjs`）会误判。

## E014 · Star 一个已删除的仓库返回 404，界面只弹窗不解释

**日期**：2026-11-24
**现象**：点首期榜单第 1 名 Leonida 的 Star，弹出错误 `HTTP 404: Not Found`，看不出是权限问题还是仓库没了。

**原因**：GitHub 对"star 一个不存在的仓库"返回 404，和"token 没权限"共用同一个状态码。前端把所有非 2xx 都当通用错误弹窗。

**修法**：
1. 宿主端识别 404 并附加 `repoMissing: true`
2. 前端看到这个标记就把按钮置灰、文字改成「仓库已不存在」、加红色边框，不再弹窗

**背景数据**：首期 10 个仓库里 **2 个已失效**（`ItsNotRexed/Leonida`、`bookwjitchieni1986/blender-ai-mcp-addon`）。周榜抓的是"本周新建"的仓库，刚建就删/改名的情况真实存在。

**教训**：**同一个 HTTP 状态码可能对应多种业务含义，要把它们区分成不同的前端行为。** 以及——抓"新建仓库"的榜单，必须预期有一定比例会很快失效。

## 排查速查表

| 症状 | 先查 |
|---|---|
| 页面空白 / 没数据 | 有没有 `data/weekly-*.json`？日期格式对不对？ |
| 某张卡片没简报 | `briefings-*.json` 里 repo 名是否和 weekly 完全一致（E005） |
| 想法提交了但没反馈 | `reports.jsonl` 的 `ideaAt` 是否等于 `ideas.jsonl` 的 `at`（E006） |
| 页面打不开 | 服务在跑吗？`node server.mjs`（E004） |
| 中文乱码 | 是用浏览器测的吗？命令行 `Invoke-WebRequest` 会变问号（E002） |
| API 返回 403 | 超限了，60 次/小时，等一会儿 |
| **改了 flags.json 没反应** | `/api/flags` 的 `meta.error` 有值吗？多半是 BOM（E009） |
| **某个功能关了，另一个也坏了** | 检查 DOM 嵌套是否制造了隐性依赖（E008） |
| **测试失败但功能正常** | 断言是不是匹配到 CSS/JS 里的同名串了（E010） |
| **页面顶部出现黄条** | 正常，说明有开关被关闭。`/api/flags` 看是哪几个 |
